# Implementation decisions

- Python 3.11+; tested here with Python 3.14.4. Standard-library argparse, asyncio and SQLite keep the runtime small. Pydantic v2, httpx, PyYAML and python-dotenv are the only required external packages.
- Ollama is the default and only production LLM adapter. `LLMProvider` and `MockProvider` allow tests without a server or cloud keys. Separate stateless chat calls and distinct prompt files isolate agent contexts. Risk uses a different default model family; analyst and PM share a model to reduce model swapping.
- CSV is the shipped market-data adapter. `DataProvider.fetch` is the extension point for a future online adapter. Automatic vendor downloads are deliberately not shipped: FCFF, reporting periods, diluted shares, corporate actions and currency normalization need explicit mapping. Missing figures stop the run. The example is synthetic, never a claim about a listed company.
- Monetary inputs use absolute currency units, shares use absolute counts, price uses currency/share, and all inputs must share one currency. FCFF is unlevered free cash flow, not levered free cash flow or operating margin. This first model requires positive revenue and FCFF and does not support banks, negative-FCFF turnarounds or multiple currencies.
- The DCF forecasts revenue using a constant growth assumption and a constant forecast FCFF margin, discounts projected FCFF, adds Gordon-growth terminal value, then adds cash and subtracts debt. Historical FCFF is used to show the observed margin. Risk independently rebuilds the arithmetic from raw inputs, then computes a nine-cell WACC/terminal-growth grid and bear/base/bull growth, margin and WACC stresses. Invalid sensitivity cells are labelled, never coerced into valid valuations. Terminal EV dependence above 75% is a warning, not an automatic rejection.
- Narrative numbers are references such as `{{data.revenue}}`, `{{assumption.wacc}}` and `{{calc.fair_value}}`. Code resolves them, supplies provenance and distinguishes observations, forecast assumptions and calculated values. Unknown references, literal numerals, common number words, external citations and markup cause rejection. This is deliberately stricter than ordinary prose. It cannot verify all qualitative claims or every linguistic way of implying a quantity; human review remains necessary.
- SQLite is authoritative for content snapshots, approvals, dependencies, ledger and audit. Markdown files are review artifacts whose full byte hashes are also checked. Approval hashes cover immutable content, including model/prompt metadata, actions and parent hashes; status and approval metadata can change only through the store. Any manual edit (even whitespace or status) invalidates the file. Preserve the edited file, audit the invalidation and require a new proposal; no automatic import or repair.
- Each stage is a separate proposal. `review` takes an analyst ID; `propose` takes a risk ID. All three proposals must be approved before PM paper execution. `changes_requested` and `rejected` are terminal review outcomes except for expiry; revisions use fresh proposal IDs. A human decision to reject is not reversible via approve. A risk agent verdict of reject or request_changes can be overridden only through a human approval with a nonempty logged reason.
- Optional senior decisions are separate staged reports, and the decision is recorded on the target proposal. Senior reports are non-executable and cannot approve themselves. No authentication system is implied: the CLI operator is the trusted human. Anyone controlling the OS account, code or SQLite database can bypass local controls. SQLite triggers provide append-only behavior through normal application operations, not cryptographic tamper resistance against the owner.
- `BEGIN IMMEDIATE` serializes all state and ledger mutations, including the kill-switch check, full dependency validation and portfolio checks. UUID filenames avoid proposal collisions. The ledger's unique proposal key enforces idempotency. Atomic file replacement is done under the DB lock; a crash can leave DB/file disagreement, which fails closed and requires regenerating research.
- PM weight is a trade-notional fraction of current paper NAV, not a target position weight. Shares are rounded down to whole units when proposing and frozen in the approved order. Paper fills use the sourced snapshot price, subject to the order limit and expiry. Portfolio and sector caps and the cash floor are rechecked against current holdings at execution. Policy changes require a new PM proposal. No shorts, leverage, slippage, fees, FX, live quote refresh or corporate-action handling are implemented. Holdings are marked at their last paper execution price.
- `halt` persists across processes and has no resume command. Start a separate `--root` workspace for a fresh educational experiment after a halt; do not erase the audit trail. In-flight model calls may finish and stage research, but subsequent execution is blocked. A fill that commits before halt takes the write lock remains a completed fill.
- `DANGEROUS_ENABLE_REAL_EXECUTION` defaults off. Setting it on refuses execution because no real executor exists. There is no path to a broker, even with the flag. The abstract `Executor` is an extension point, not a real integration.
- Context admission uses a conservative UTF-8 byte count plus template overhead and an output reserve. It may reject prompts that a tokenizer would fit. This avoids silently truncating research; increase `num_ctx` only within the installed model and hardware limits. Token budgets reserve this same conservative amount per attempt. Wall-clock limits include semaphore waiting and generation. Ollama's own internal model limits cannot be guaranteed by the client.
- Per-process concurrency defaults to one. Independent tickers can be queued together with `ws analyze DEMO OTHER`; model calls are capped. Multiple separate CLI processes do not share a model semaphore; use one command to respect the configured local-hardware budget.
- Seed, temperature, prompt hashes and pre/post model digests are recorded/checked. This aids reproducibility but does not promise bit-identical GPU generation or prevent a malicious local Ollama server from lying. Structured schema validation retries a bounded number of times; provenance or business-rule failures stop cleanly without staging the invalid agent response. Reasoning blocks and separate Ollama thinking output are not stored.
- The public [ai-berkshire repository](https://github.com/xbtlin/ai-berkshire) was consulted for its adversarial multi-agent pattern. No source code was copied and there is no dependency. Ollama request behavior follows its [chat API](https://docs.ollama.com/api/chat) and [model tags API](https://docs.ollama.com/api/tags).
